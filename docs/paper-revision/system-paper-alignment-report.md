## 2. In-Depth Technical Gaps (Codebase vs. Paper)

### A. The Dual-Mode AI Chatbot (`heritage-chat-flow.ts`)
*   **Code Reality:** The system does not run a naked LLM prompt. It implements a highly robust **Dual-Mode Architecture**:
    1.  **Deterministic Local Mode:** If the query is off-topic, a friendly chat greeting, a system question (e.g. asking "What is Handumanan?"), or if the Gemini API key is missing/quota-limited (429), `shouldAnswerLocally` triggers local processing. It uses custom regex and string scoring to return local facts directly from `HERITAGE_SITES` without hitting the Google Gemini API.
    2.  **AI Mode (Genkit + Gemini 2.5 Flash):** Only complex comparisons, route-themed queries, and open historical questions bypass local routing. RAG is achieved by bundling a 45-site directory snapshot into the system prompt and binding the `searchSites` Genkit tool to search Firestore on-the-fly.
*   **Paper Gap:** The paper treats the chatbot as a simple wrapper around the Gemini API, neglecting the local rule-based fallback and the `searchSites` tool routing. This makes the system seem vulnerable to internet outages and rate-limiting when, in reality, it is built to degrade gracefully.

### B. Timezone-Aware Open/Closed Parser (`site-availability.ts`)
*   **Code Reality:** The system implements a robust availability state machine. It uses the `Asia/Manila` timezone to determine current time regardless of the client browser's local timezone. It parses day-of-week strings (e.g., `Mon-Fri`) and time strings (`8:00 AM - 5:00 PM`), handles special conditions (e.g., `24 Hours`, `Open Access`, `Daylight Hours`), and checks for `demolitionStatus === 'Demolished'` and `isActive === false` to filter out unavailable sites.
*   **Paper Gap:** The paper lists "Open/closed site status" in the test plan, but never explains *how* the system achieves this. The exact logic of string parsing, timezone-locking to Manila, and active filtering needs representation in the system's design sections.

### C. Two-Layered Backup Routing (`routing-service.ts` & `heritage-chat-flow.ts`)
*   **Code Reality:** When the Google Routes API fails, hits quota ceilings, or is unavailable during local development, the system executes a **two-layered backup route algorithm**:
    1.  **OSRM Backup Router:** Hits `https://router.project-osrm.org/route/v1/driving/` to fetch actual road-network distances and estimated travel times.
    2.  **Coordinate-Based Secondary Backup:** Uses the Haversine formula to compute straight-line distance, multiplies it by `1.35` to estimate road curvature, and divides by a standard 22 km/h city driving speed to estimate duration.
*   **Paper Gap:** The paper defines "Backup Route Estimate" in Chapter 1 but describes it only as an approximate fallback, completely omitting the OSRM integration and the mathematical secondary fallback.

## 4. Final Alignment Recommendations for Re-Defense

1.  **Emphasize Graceful Degradation (API Outage Resilience):** In the re-defense presentation, make sure to highlight that the AI chatbot and itinerary planner are **not** single points of failure. Under API outages (e.g., Gemini rate limits or Google Maps outages), the system degrades gracefully into deterministic local flow mode (rule-based local facts and local itinerary sequencing) and backup routing (OSRM and Haversine coordinate calculations).
2.  **Clarify the Firebase-to-AI Pipeline:** Explain to the panel that the AI does not hallucinate arbitrary places because it is restricted via **Retrieval-Augmented Generation (RAG)**. Active heritage site records in Firebase Firestore are passed directly to the Gemini model prompt context, meaning any administrative updates to status, hours, or coordinates immediately influence chatbot and planner output.
3.  **Tense Standardization:** Run a final pass through the paper to convert any remaining future-tense verbs (e.g., *"will be collected"*, *"will use"*) to completed-study past-tense (e.g., *"were collected"*, *"used"*).
